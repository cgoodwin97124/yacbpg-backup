- **Copy, not a link (the author's decision).** Picking a description **copies its text** into the panel's box; editing the library copy afterwards does **not** rewrite panels that already took it (pick it again to replace the box). - **Why copy-with-provenance rather than a live id reference.** A live reference would have made the panel's text a *view* of the library (a new thing to keep in sync across 24 panels × 3 character slots × every page, plus a new failure mode when a description is deleted mid-edit) and would have changed the saved project shape, which would have forced a schema version bump and a migration for a purely cosmetic gain. Copy keeps the panel self-contained, keeps backups/exports byte-compatible, and matches the Basic Description precedent the author already approved.
- **The new library type.** `'Panel Description'` is a first-class `libObjects` type with the id prefix **`pd-`** (`LIB_TYPE_PREFIX` in `src/core/library-core.js`, and `normaliseLibType` in **both** `src/core/library-core.js` and `src/core/schema.js`, so a hand-edited project or an old file cannot drop the type on load). It gets a **💬 Panel Descriptions** bucket in 📚 Library (always shown, beside Characters / Locations / Actions) with the same rows, the same "no ✎ rename" rule, the same ⤒ *offer to My catalogue* / ⤓ *copy in from My catalogue*, and the same deletion semantics — deleting one never disturbs a panel that already took its text. `migrateLibObjects`'s prune list gained the type so an unknown-type item is still dropped by the migration.
